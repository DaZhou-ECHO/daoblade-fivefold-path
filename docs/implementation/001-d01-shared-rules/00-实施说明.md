# 001 / D01 共享规则与不可变战斗快照

日期：2026-10-20。依据初版策划00、01；范围为一个完整底层切片。基线 `0edf7136246d59c79853dd89dc8a72f5ffbd067c`，新分支 `work/001-d01-shared-rules`。

## 解决的问题

前后端分别维护默认档、元素/卦路标识与部分计算，长期多方向修改容易漂移。原 calculateStats 返回的 loadout 直接引用存档对象，开战后外部改动该数组会改变本局配置。JSON按字母排序还可能改变UI枚举顺序。

## 实际实现

1. `static/data/rules/legacy-v1.json` 成为现有默认档、五行/卦路/词条目录、容量与有序ID的共用数据源。它明确是旧规则，不是最终完整阵盘。
2. Python `shared_rules.py` 从该文件读取并提供复制后的规则、元数据、默认档、五行计算和出战校验。game_rules.py保留旧导入名称和完整服务端存档校验。
3. 独立 `static/js/rules.js` 提供纯函数适配器；game.js只保留界面调用包装，原计算公式移入适配器，未改倍率、上限、伤害或掉落。
4. 创建战斗时复制配置并深度冻结快照，BattleGame实际读取snapshot.stats；原档或下一局变化不再污染当前局。生命、冷却、位置等可变战斗状态仍在player，不写入只读快照。
5. ProgressionState将旧层位映射为带ID的只读节点视图，例如legacy:qian:1；尚不用于保存或替代旧cultivation。未来新阵盘另设规则适配器，不能把24个旧节点视图当成已经交付40节点。
6. `/api/rules`公开同一配置与契约元数据，页面安全嵌入该配置后加载rules.js。存档响应增加contract信封，原state与revision保持兼容；旧SQLite数据不自动改写。
7. 显式声明未知规则集/版本会被拒绝，不能拿尚未实现的新规则标记套用旧规则。缺省规则标识的历史存档继续按legacy-v1解释。
8. 显式element_order/trigram_order保持既有顺序，不依赖JSON对象键顺序。

## 规则与版本的边界

| 字段 | 含义 | 当前值 |
|---|---|---|
| contract_version | 公共接口形状 | 1 |
| ruleset_id | 使用哪套玩法解释 | legacy-v1 |
| schema_version | 本适配器的存档结构 | 1；对应历史state.version |
| rules_version | 该规则集内部规则修订 | 1 |
| revision | 数据库并发写入计数 | 按现有每账号存档递增 |
| 001 | 本次开发工作编号 | 不写入存档或冒充正式版本 |

当前页面仍采用旧三层永久规则和全身主副属性。策划中的可拆换测试、本位五行、独立技能元素和境界预算需要后续新规则集实施；这轮没有放开旧档后端约束，也没有把未确定数值写入配置。
