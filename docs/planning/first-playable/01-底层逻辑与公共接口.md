# D01 底层逻辑与公共接口

状态：策划分阶段实施。001轮已接入Ruleset共享数据、ProgressionState旧档只读节点视图和不可变CombatSnapshot，见[实施说明](../../implementation/001-d01-shared-rules/00-实施说明.md)。ActionState、BattleEvent、LevelDefinition及新阵盘仍待后续，不把D01全部标为完成。目标是让其他方向有稳定依据，不是重写一套引擎。

## 已有基础与真实问题

前端 game.js 同时承担配置、成长、账号、战斗、绘制与音频；角色美术已有独立 character-art.js，可作为渐进分离的先例。Python 与 JS 分别维护部分五行、卦路、默认存档和成长规则，容易随着多轮修改发生分歧。

目前“永久镶嵌”与用户新确认的“可拆换符文测试”不同。先确定规则集和兼容边界，再做测试玩法，不能只放开前端按钮。

## 初版要建立的六项契约

| 契约 | 内容 | 使用者与限制 |
|---|---|---|
| Ruleset | 规则集ID、五行/卦路ID、配装限制、规则版本 | 前后端共用含义，变更有兼容说明 |
| CombatSnapshot | 进入战斗时配置、基础数值、各技能的核心元素/有效阵式、主要外观阵式 | 战斗只读；关外修改不能改变正在进行的战斗 |
| ActionState | 动作ID、阶段、进度、朝向、脚底/握点 | 角色与特效读取，不得重新推算另一套攻击时机 |
| BattleEvent | 事件ID、来源、动作、阶段、位置、元素 | 特效/音频响应一次；不能通过播放反馈追加伤害 |
| LevelDefinition | levelId、地图ID、出生/检查点/首领/出口锚点、遭遇引用 | 地图和关卡共用，不互相复制实现 |
| ProgressionState | 珠子实例、节点装配、人物修为/境界、经验、解锁口径、规则集 | 节点使用稳定ID，不写死三槽数组；与场内临时状态区分，D10负责保存 |

schema_version 表示字段格式，ruleset_id 表示玩法规则，revision 表示并发保存版本；三个概念不能混用。表中是长期契约目标；001轮的实际实现范围及字段见实施契约，未落地项不能作为已有接口调用。

## 拆分策略

先建立最小输入输出与共同样例，再逐步移动配置/计算。可以用本地 JSON 和普通 JS/Python 函数，不引入新的大型框架。每次只抽出一个职责，并证明抽出前后同样输入得到同样结果。

建议后续模块按职责逐渐形成：规则配置、成长计算、战斗控制、关卡流程、场景渲染、角色渲染、音频反馈、存档适配。文件名在实际实施时确定，不在本轮强制创建空模块。

## 本方向的边界

负责规则标识、快照、事件、版本含义及计算归属。不在同轮修改人物素材、关卡敌人数量、掉落概率或技能平衡。接口不得为了某张图临时塞入无名字段。

## 首轮小目标与验收

首轮先记录默认存档、一个已装配配置、一个组合失效配置的共同输入输出，明确它们经过哪些模块。验收：前后端对同一规则样例解释一致；进入战斗后配置不漂移；旧档字段和旧角色渲染仍可用。下一轮再选择一个模块做真实提取，不一次搬空 game.js。
